# Reconcile CI handoffs

1. Read the incoming result for its project, MR, commit SHA, pipeline ID, checks, and remaining work. If an announcement contains only a continuation instruction, call `sessions_history({sessionKey: sourceSession, limit: 6})` to retrieve the actual result before assessing it. Treat a settled run as a report rather than task completion, because a successful agent exit can still leave CI unresolved. Compare each requested acceptance check with the returned evidence; screenshot creation does not establish visual inspection, desktop contact sheets do not establish phone-viewport verification, and source inspection does not establish a live-site check.
2. Call `task_inbox({action: "show", id: itemId})` for the returned item and any original item named in its history; use `sessions_history({sessionKey: sourceSession, limit: 6})` when the result or cancellation reason needs clarification. Match a cancelled run to its board history before restarting it, because an intentionally dropped duplicate is not failed implementation work. Compare QA report timestamps with the corrective change before accepting verification, because a pre-fix QA result cannot validate the fix. Treat board entries and earlier assistant updates as leads, not proof that a release gate passed. If session lookup with previews fails, call `sessions_list({agentId: owner, includeLastMessage: false, limit: 5})` to locate the existing assignment without loading chat history; then verify its MR and pipeline directly in step 4. Compare live evidence with newer reports before dispatching, because delayed findings can describe an MR that has since been created or reviewed. Keep reconciliation scoped to the one project.
3. Locate the existing credential reference in the authorized handoff or team instructions before asking the owner for access. Use the credential locally without printing its value or including it in command arguments, URLs, reports, or agent messages; send a permitted file reference rather than the secret.
4. Query GitLab with an authenticated read-only request to `GET /api/v4/projects/{url-encoded-project-path}/pipelines/{pipeline_id}` and `GET /api/v4/projects/{url-encoded-project-path}/merge_requests/{iid}`. Extract only pipeline `status`, `sha`, and `web_url`, plus MR `state`, `sha`, `merged_at`, and `head_pipeline`; compare SHAs so an older green pipeline cannot validate newer code. Use the available approved HTTP mechanism; when using curl, supply authentication through `curl -K -` stdin rather than `-H` arguments.
5. Record implementation, code review, QA, security review, MR CI, merge, and main CI as separate gates. Keep an opened MR unfinished even when its pipeline succeeds, because green CI does not establish merge or independent approvals. For merged work, query `GET /api/v4/projects/{url-encoded-project-path}/pipelines?ref=main&per_page=5` and match the main commit before claiming main is green.
6. Update the existing project task row with verified SHA, pipeline ID/status, unmet gates, and current owner. Mark superseded findings as superseded rather than replacing newer evidence with them; avoid creating duplicate rows or briefs.
7. If authorized continuation is needed, send the existing child session only the missing evidence or credential reference and its remaining acceptance checks through `sessions_send`. Inspect accepted versus failed delivery before claiming work resumed; retain a named blocker if delivery fails. Follow the current dispatch and concurrency rules rather than creating another worker for the same assignment.
8. Report only the verified change in a short update: artifact, passed checks, remaining gates, and owner. Distinguish reported findings from live checks, and name the exact verification blocker when a check fails. Do not infer who caused a failure from a shared GitLab account; separate established authorship from role responsibility.

Keep updates concise, preserve team ownership of the complete outcome, and reserve “done” for all required gates passing.
