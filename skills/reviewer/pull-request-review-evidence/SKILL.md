---
name: pull-request-review-evidence
description: "When reviewing, rebasing, or merging pull requests, establish exact diff scope and independently prove CI, deployment, and visual results."
---

1. Read the assignment and repository instructions; record the repository, PR, permitted mutations, required QA/security gates, and production approval boundary before taking action.
2. Fetch the base and feature branches with `git fetch origin <base> <branch>` and record `git rev-parse origin/<base> origin/<branch>`; cached tracking refs cannot establish current remote state.
3. Review `git diff --stat origin/<base>...origin/<branch>` and `git diff origin/<base>...origin/<branch>`; use the three-dot merge-base diff to identify changes introduced by the PR rather than mistaking missing base commits for reversions. Check ancestry separately with `git log --oneline origin/<branch>..origin/<base>`.
4. Create an isolated review worktree with `git worktree add -b review-<identifier> <review-path> origin/<branch>`; leave another contributor’s checkout and uncommitted files untouched. If authorized to rebase, run `git -C <review-path> rebase origin/<base>`, stop on conflicts covered by the brief, and inspect the resulting diff and preserved base safeguards.
5. Before an authorized force-push, record the remote branch SHA with `git ls-remote origin refs/heads/<branch>` and the intended commit with `git -C <review-path> rev-parse HEAD`. Inspect that commit and push the explicit SHA using `git push --force-with-lease=refs/heads/<branch>:<observed-remote-sha> origin <reviewed-sha>:refs/heads/<branch>`; an explicit source and lease protect against stale local branch names and concurrent contributor updates. Verify the resulting remote SHA before continuing.
6. Run the repository-defined lint, test, build, and browser checks on the exact candidate commit. Read failures and CI job logs before diagnosing them; when markup changes, verify selector updates preserve assertions rather than merely making the test green. Treat terminated or output-free checks as unverified.
7. Inspect GitHub API `repos/<owner>/<repo>/pulls/<number>`, `commits/<sha>/check-runs`, `commits/<sha>/status`, and Actions runs for the exact head SHA through available authenticated tooling. Check workflow runs as well as checks/statuses before concluding that CI is absent; zero results from one API are not evidence of no pipeline.
8. Merge only after the required review, QA, security, and CI gates pass. Verify `merged` and `merge_commit_sha` from the PR API, `sha` from `commits/<base>`, and the matching deployment workflow conclusion; do not infer merge or deployment from stale local history. If that workflow is still running, do not wait: end with `RESULT: waiting` and its run link, and the guard follows it.
9. For UI work, compare cache-busted screenshots from the project’s own authorized live URL with the owner’s actual reference at 1920x1200 and 390x844. Save evidence under `qa/evidence/<project>/<item>/` and describe the required elements shown; HTTP 200 and matching bundle hashes establish health or delivery, not visual acceptance. For motion-dependent criteria, capture the required timed frame sequence rather than relying on a still.
10. Report the exact reviewed and merged SHAs, checks actually completed, deployment run ID, evidence paths, and remaining gaps in the assigned topic using the messaging tool. Keep writer-reported checks separate from independently observed results, and re-check the same authoritative source before issuing a correction or retraction.
